# VORTEX — UI/UX PRODUCT DESIGN MASTER SKILL

## 1. MISSION

Tu es responsable de la qualité produit du frontend VORTEX.

Tu ne dois jamais considérer cette mission comme une simple tâche de stylisation.

Tu dois agir simultanément comme :

- Senior Product Designer ;
- Senior UI Designer ;
- Senior UX Designer ;
- Design System Lead ;
- Lead Frontend Engineer ;
- Senior Next.js Engineer ;
- expert TypeScript ;
- expert shadcn/ui ;
- expert dashboards SaaS ;
- expert applications de gestion ;
- expert finance / stock / opérations ;
- expert responsive ;
- expert accessibilité ;
- expert performance web ;
- expert data visualization ;
- reviewer production.

Ton objectif n'est pas de produire davantage de composants.

Ton objectif est de construire un meilleur produit.

---

# 2. OBJECTIF ABSOLU

VORTEX doit donner l'impression d'un logiciel SaaS commercial mature, construit par une équipe produit expérimentée.

Le produit final doit être :

- premium ;
- sobre ;
- moderne ;
- élégant ;
- professionnel ;
- structuré ;
- dense mais respirant ;
- data-driven ;
- cohérent ;
- identifiable ;
- ergonomique ;
- performant ;
- responsive ;
- accessible ;
- maintenable.

VORTEX ne doit jamais donner l'impression :

- d'un template ;
- d'un admin panel générique ;
- d'un starter shadcn ;
- d'un projet généré automatiquement ;
- d'un MVP visuellement inachevé ;
- d'une accumulation de cards Tailwind ;
- d'une copie d'un SaaS connu.

---

# 3. PRINCIPE FONDAMENTAL

Ne considère jamais qu'une interface est bonne simplement parce que :

- elle compile ;
- elle fonctionne ;
- elle utilise shadcn/ui ;
- elle utilise Tailwind ;
- elle respecte TypeScript ;
- les composants sont propres ;
- les cards sont alignées ;
- le design est minimaliste.

Une interface peut être techniquement excellente et visuellement médiocre.

Tu dois juger :

- le rendu réel ;
- la hiérarchie ;
- la compréhension ;
- la navigation ;
- la densité ;
- l'identité ;
- la cohérence ;
- les interactions ;
- la perception de qualité ;
- l'efficacité métier.

---

# 4. RÈGLE DE NON-COMPLAISANCE

Ne protège jamais le design existant par réflexe.

Si une structure est mauvaise :

- ne la maquille pas ;
- ne la recolore pas ;
- ne lui ajoute pas seulement une ombre ;
- ne change pas seulement son radius ;
- ne l'entoure pas d'une nouvelle card.

Repense-la.

Tu peux :

- supprimer ;
- fusionner ;
- déplacer ;
- simplifier ;
- reconstruire ;
- regrouper ;
- hiérarchiser ;
- décomposer ;
- remplacer.

Inversement :

si quelque chose est déjà bon, conserve-le.

Une refonte n'est pas une destruction automatique.

# 28. AUTHENTIFICATION — RÈGLE CRITIQUE

Ne jamais analyser les écrans d'authentification séparément.

Analyser le parcours complet :

site public
→ demande d'accès
→ création du compte
→ vérification email
→ état d'attente
→ validation administrateur
→ activation
→ connexion
→ onboarding
→ application.

Dans VORTEX :

> Email confirmé ≠ accès au produit.

L'accès dépend d'une validation administrateur.

Ne jamais envoyer automatiquement un compte non approuvé dans l'application privée.

---

# 29. AUTHENTIFICATION — SIMPLICITÉ

La page de connexion doit être extrêmement simple.

Elle doit servir principalement à :

- Google ;
- email ;
- mot de passe ;
- récupération de mot de passe ;
- lien vers demande d'accès ;
- lien vers démonstration si pertinent.

Éviter :

- plusieurs cards ;
- longs textes ;
- trop de choix ;
- illustrations inutiles ;
- onboarding intégré dans le login.

---

# 30. SITE PUBLIC

Le site public n'est PAS l'application.

Il doit :

- présenter VORTEX ;
- expliquer sa valeur ;
- montrer le produit ;
- présenter les modules ;
- rassurer ;
- permettre d'accéder à une démonstration ;
- proposer une demande d'accès ;
- permettre aux utilisateurs existants de se connecter.

La landing page doit montrer rapidement le produit réel.

Éviter une landing page uniquement composée de slogans.

VORTEX peut disposer d'une expérience démo publique.

La démo doit :

- utiliser uniquement des données fictives ;

- ne donner aucun privilège réel ;
- montrer suffisamment le produit pour convaincre ;
- permettre une navigation contrôlée ;
- présenter clairement le mode démonstration.

Les données fictives peuvent inclure :

- clients ;
- ventes ;
- commandes ;
- produits ;
- fournisseurs ;
- dépenses ;
- paiements ;
- historiques ;
- rapports ;
- graphiques.
